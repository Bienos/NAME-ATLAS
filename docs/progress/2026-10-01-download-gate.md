# 2026-10-01 — TASK-064: the sign-in gate on the share-card image

Branch `claude/friendly-brown-6n5iwu`, built on `main` @ `65ed574` (#68). Task file: `tasks/064-download-gate.md`. Decision: `docs/adr/0027-free-accounts.md` §5.4, amended here.

## Why

The project owner said "go" on the plan that names this as the step after TASK-063, from their earlier words "at the end should be log in button to be able to download a share card". **It does nothing in production until accounts are switched on:** with the five variables unset the route, the deck and the pages are what they were.

## What changed

- **`download-gate.ts`** (new): turns the request's session cookie into a verdict: `off` (accounts off), `open` (the cookie names a live session), `sign-in` (no cookie, or one that names no session; no cookie costs no database read) or `unavailable` (the accounts database cannot say).
- **`share-route.ts` and the two route files:** the verdict is applied after the card is known and before the register is read, so an anonymous request costs no register query and learns nothing about which surnames exist. `sign-in` is a 401 with `Cache-Control: no-store` and a `WWW-Authenticate` challenge; `unavailable` a 503 with `Retry-After`; `open` serves the image with `Cache-Control: private, no-store` (a shared cache that kept the public header would hand the image to a reader with no session); `off` is the old public header, unchanged.
- **`safeNext`** (`account-paths.ts`): the one place that decides where a sign-in may return to: `/pl/nazwisko/{slug}` or `/en/surname/{slug}` of this site, optionally with `?view=cards`, the slug as `canonicalSlug` writes it (letters percent-encoded, apostrophe kept). The sign-in page puts it in a hidden field and sends an already signed-in reader there; the sign-in action follows it only after checking it again, keeps it on a failed attempt, and drops an unsafe one.
- **The deck:** on a 401 the button shows, for that card only, "Obraz zapiszesz po zalogowaniu." / "Sign in to save the image." and a link to the sign-in page carrying `next` (`deckSignIn` in `deck.tsx`; given by `surname-page.tsx` only when accounts are on). The live region is always in the page so a screen reader announces the text when it appears.
- **Left as it was on purpose:** the 1200 × 630 `opengraph-image`, the "Zapisz obraz" link beside it and the button that shares the page's link. Whether any of them should wait for a sign-in is the owner's call (ADR-0026 §1 quotes "click login to share it with friends"); each is a small change. `next` is not carried through sign-up and the mail, because the mail's link would then hold the surname the reader looked at, which the privacy notice does not describe.
- **Docs:** the task file, ADR-0027 §5.4, `docs/CODEMAP.md`, `STATUS.md` (including the lines #68 had made untrue: the deployed row, the database row, the "VM side built and not yet run" text, the next steps).

## Not verified

- **Production.** This is not deployed. With accounts off there, the change does nothing; it was checked on a local `next start`.
- **A switched-on site.** There is no Resend account, sending domain or the five variables. The browser run used a stand-in for the mail endpoint, a local PostgreSQL 16 and PgBouncer-less connection, and a fixture register of a few dozen surnames (NOWAK's deck has two cards, the count-only deck, so only the summary card was downloaded; the other cards' images are the same route and gate).
- **The 503 end to end.** The accounts database was not taken down in the browser run; the verdict and the route's answer are unit-tested.
- **Vercel's edge cache.** The image's `Cache-Control` is `private, no-store` for a session and `no-store` for a refusal, which Vercel's CDN should not keep. A copy cached before accounts are switched on (`s-maxage` one hour, `stale-while-revalidate` a day) is assumed to be gone because switching on is a redeploy, which gets a new cache; that was not checked.
- **A reader who signs up on another device.** The sign-up's mail link does not carry the page back; the reader opens the deck again and presses the button. Shown in the browser only for the same browser.
- **The web share sheet on a phone.** The deck's `navigator.share` path is untouched and was not run; the 401 branch precedes it.
- **Assistive technology.** The prompt is in a `role="status"` region that is in the page from the start; no screen reader was used.
- **`WWW-Authenticate: Cookie`** is a made-up scheme chosen so that no browser shows a login dialog for a `fetch`; the browser run showed none in Chromium.
