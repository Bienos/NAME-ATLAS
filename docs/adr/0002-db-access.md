# ADR-0002 — PostgreSQL access and query layer

- **Status:** Accepted
- **Date:** 2026-09-18
- **Deciders:** project owner + control-plane session
- **Depends on:** ADR-0001 (TypeScript/PostgreSQL P0 stack)

## Context

The canonical corpus fixes PostgreSQL as the system of record but never names a TypeScript data-access layer — a search of `docs/canonical/10–23` returns no mention of Prisma, Drizzle, Kysely, TypeORM or any equivalent. Without a decision here, every implementation session would choose or reconsider one, and the schema would drift between sessions.

The schema this layer must serve is not a generic CRUD schema. From `docs/canonical/11`, `12`, `15` and `23` it requires:

- PostGIS geometry columns with valid-time semantics;
- `pg_trgm` indexes and similarity operators for candidate generation;
- JSONB payloads with per-type versioned schemas (`Claim.structured_value`, `EvidenceItem.structured_value`) and JSONB queries;
- partial and expression indexes (active claims, active entitlements, pending outbox rows, active run coalescing keys);
- `ON CONFLICT` upserts and idempotent imports;
- advisory locks and an outbox pattern;
- UUIDv7 keys generated application-side;
- staged, explicitly reviewable migrations (Groups A–G in `docs/canonical/23` §9);
- Testcontainers-backed integration tests that exercise real constraint and transaction behaviour (`docs/canonical/17` §3.2).

The optimisation target is therefore PostgreSQL-first behaviour and the ability to write explicit SQL without fighting an abstraction — not developer convenience on simple queries.

## Decision

**Use Kysely as the type-safe query builder over the `pg` (node-postgres) driver, with hand-written SQL migrations executed by Kysely's built-in migrator, and database types generated from the migrated schema.**

Concretely:

| Element | Choice |
|---|---|
| Driver | `pg` (node-postgres), one pooled connection per app/worker process |
| Query layer | Kysely (typed query builder; `sql` template tag for anything it does not model) |
| Migrations | one file per migration, containing explicit SQL DDL, run by Kysely's `Migrator` + `FileMigrationProvider` |
| Migration naming | zero-padded, ordered, grouped to match `docs/canonical/23` §9 migration groups |
| Types | generated from a migrated database (e.g. `kysely-codegen`), checked in, regeneration verified in CI |
| Extensions | `postgis` and `pg_trgm` enabled by the first migration |
| Keys | UUIDv7 generated in application code |
| Integration tests | Testcontainers PostgreSQL image with PostGIS, migrations applied from scratch per suite |

Rules that follow:

- Migrations are **SQL**, reviewed as SQL. No migration is generated by diffing a model file.
- PostGIS, `pg_trgm`, partial indexes, expression indexes, extensions and constraints are expressed directly in that SQL. They are never approximated by an ORM feature.
- Complex read paths (trigram candidate generation, coverage aggregation, ranking) may be written as raw `sql` queries returning typed rows. Dropping to SQL is the normal, expected path — not an escape hatch.
- No lazy loading, no entity change-tracking, no repository framework. Domain services own persistence logic per bounded context (`ARCHITECTURE.md` §2).
- Generated types are derived from the real schema; the schema is never derived from TypeScript.

## Alternatives considered

**Prisma.** Best-in-class ergonomics and the most familiar option. Rejected: the schema lives in a proprietary DSL that does not model PostGIS geometry, trigram indexes, partial/expression indexes or several constraint forms, so the parts of this schema that matter most would sit outside the model and be applied through escape hatches; migrations are generated from that model rather than authored as reviewable SQL; raw queries return weakly typed results. The abstraction would be fought on every high-value query.

**Drizzle.** Strong second choice and a genuine contender — PostgreSQL-first, SQL-like, good raw-SQL support, real `pg_trgm`/PostGIS escape routes. Rejected because its migrations are generated by diffing a TypeScript schema definition, which makes the TS file the source of truth and the SQL an artifact. For a schema whose correctness lives in constraints, partial indexes and extension behaviour, we want the SQL authored and reviewed directly, with types flowing *from* the database. The margin over Kysely here is small; if Kysely's type generation proves unworkable, Drizzle is the first fallback.

**node-postgres alone, SQL-first.** Maximum control, zero abstraction. Rejected: no compile-time safety over column names or result shapes across a schema this large, and every query would hand-maintain its row type. Kysely gives exactly this control plus type checking, over the same driver.

**TypeORM / Sequelize / MikroORM.** Rejected: heavier ORM semantics (entity managers, change tracking, lazy loading) that conflict with an evidence-lineage model built on immutable, versioned rows and explicit provenance.

## Consequences

**Positive**

- The database schema is authored and reviewed as PostgreSQL SQL; nothing about PostGIS, `pg_trgm`, JSONB or partial indexes has to be worked around.
- Types are checked against the schema that actually exists, because they are generated from it.
- Testcontainers tests exercise the real migration path from empty database to current schema, catching drift and constraint errors in CI.
- Immutability and idempotency rules (never overwrite a snapshot, `ON CONFLICT` imports, outbox) are expressed directly.
- Low lock-in: Kysely is a query builder over `pg`, so raw SQL and the driver remain available underneath.

**Negative / accepted costs**

- No automatic migration generation. Every schema change is written by hand — deliberate, and slower for trivial changes.
- Database types must be regenerated after each migration, and CI must verify the checked-in types match a freshly migrated database, or they will silently rot.
- Less scaffolding than Prisma: no studio, no seeded client, no generated CRUD.
- Kysely models less of PostGIS than a dedicated spatial ORM would; spatial queries will be raw `sql`. Accepted — spatial logic is not P0 and geometry is best expressed in SQL anyway.

**Obligations for TASK-001**

- Wire the migration mechanism and one bootstrap migration enabling `postgis` and `pg_trgm`.
- Wire the Testcontainers harness so migrations run from scratch against a real PostgreSQL+PostGIS image.
- Wire type generation and a CI check that generated types are current.
- Do **not** create canonical domain tables. Schema Groups A/B belong to TASK-004 and TASK-005.

## Do not revisit unless

- Kysely's type generation cannot be made to work reliably against the migrated schema in CI (then: Drizzle, same migration philosophy); or
- a demonstrated, measured performance or correctness problem is traced to the query layer itself rather than to the SQL written through it; or
- the P0 stack decision in ADR-0001 changes.

Developer preference, familiarity with another tool, or a session's convenience are **not** reasons to revisit this. Individual implementation sessions may not substitute a different data-access layer.
